# 07 - LeetCode (Design a Coding Platform)

**Source:** https://www.hellointerview.com/learn/system-design/problem-breakdowns/leetcode
**Author:** Evan King (Hello Interview) · **Difficulty:** Medium · **Pattern:** Managing Long Running Tasks

---

## Understanding the Problem

LeetCode is a platform that helps engineers prepare for coding interviews. It offers a large collection of problems (easy → hard), lets users submit solutions and get feedback, and runs periodic coding competitions.

**Key scale insight:** LeetCode only has a few hundred thousand users and ~4,000 problems. Relative to most system design interviews, this is a **small-scale system** — keep this in mind, as it significantly impacts the design (simplicity beats over-engineering here).

## Functional Requirements

**Core:**
1. Users should be able to view a list of coding problems.
2. Users should be able to view a given problem and code a solution in multiple languages.
3. Users should be able to submit their solution and get instant feedback.
4. Users should be able to view a live leaderboard for competitions.

**Below the line (out of scope):**
- User authentication
- User profiles
- Payment processing
- User analytics
- Social features

Assume users are already authenticated with user ID stored in session/JWT.

> Tip: Listing out-of-scope features is a "nice to have" — it shows product thinking and lets the interviewer reprioritize. But don't waste time if features aren't coming quickly.

## Non-Functional Requirements

**Core:**
1. Prioritize **availability over consistency**.
2. Support **isolation and security** when running user code.
3. Return submission results **within 5 seconds**.
4. Scale to support competitions with **100,000 users**.

**Below the line (out of scope):**
- Fault tolerance
- Secure transactions for purchases
- Well-tested / easy deployment (CI/CD)
- Regular backups

## The Set Up

### Planning the Approach
For user-facing product-style questions: build the design up sequentially, going one-by-one through the functional requirements. Then use the non-functional requirements to guide deep dives.

### Core Entities
1. **Problem** — problem statement, test cases, expected output.
2. **Submission** — the user's code submission and result of running it against test cases.
3. **Leaderboard** — leaderboard for competitions.

(User is implied; not necessary to call out. Don't detail columns yet — that comes later.)

### API Design

Go one-by-one through functional requirements, ensuring at least one endpoint per requirement.

```
# 1. List problems (paginated; return only a subset of fields — title, id, level, tags)
GET /problems?page=1&limit=100 -> Partial<Problem>[]

# 2. View a specific problem (code stub in preferred language, default e.g. python)
GET /problems/:id?language={language} -> Problem

# 3. Submit a solution
POST /problems/:id/submit -> Submission
{
  code: string,
  language: string
}
# userId NOT passed in — comes from session/JWT

# 4. Live competition leaderboard
GET /leaderboard/:competitionId?page=1&limit=100 -> Leaderboard
```

> **Security red flag to avoid:** never pass userId or timestamps from the client in body/query params. Client data can be manipulated. User identity comes from session/JWT; timestamps are generated by the server.

## High-Level Design

Most interview systems suit microservices, but **not this one** — the system is small enough that a **simple client-server (monolithic) architecture** is more appropriate; the overhead of managing many services isn't worth it.

### 1) View a list of coding problems
- **API Server**: handles requests, returns data, handles pagination.
- **Database**: stores problems. SQL or NoSQL both work; chose **DynamoDB (NoSQL)** since there are no complex queries and test cases can be nested as a subdocument in the problem entity.

Problem schema:
```json
{
  "id": "string",
  "title": "string",
  "question": "string",
  "level": "string",
  "tags": ["string"],
  "codeStubs": { "python": "...", "javascript": "...", "typescript": "..." },
  "testCases": [{ "type": "string", "input": "JSON", "output": "JSON" }]
}
```
Code stubs per language are entered by an admin or generated by an LLM from one example.

### 2) View a problem and code a solution
Client requests `GET /problems/:id`; server fetches from DB and returns statement + code stub. Use a **Monaco Editor** in the browser for coding.

### 3) Submit a solution and get instant feedback

The interesting part — how do we run untrusted user code safely?

#### Bad: Run code directly in the API server
Save code to a local file, run it, capture output. **Terrible idea:**
- **Security:** malicious code could delete data, exfiltrate it, mine crypto, launch DDoS attacks.
- **Performance:** CPU-intensive code (infinite loops, memory leaks) can crash the server.
- **Isolation:** a crash takes down the API server and all in-flight requests.

#### Good: Run code in a Virtual Machine (VM)
Isolated environment on the physical server; easily reset; a crash in the VM doesn't affect the host or other users.
- **Challenge:** VMs are resource-intensive and slow to start; lifecycle management is costly and wasteful.

#### Great: Run code in a Container (Docker) ← chosen
Containers provide isolation like VMs but are much more lightweight and faster to start.
- **VMs:** full OS per VM via hypervisor — larger, slower to start, strongest isolation.
- **Containers:** share host kernel, isolate processes; include app + dependencies but no full OS — lightweight, fast start, less isolation but much more resource-efficient.
- Create one container per supported runtime (Python, JavaScript, Java, …) with dependencies installed; **reuse containers across submissions**.
- **Challenge:** since containers share the kernel, must configure/secure them so users can't break out, and enforce resource limits (see deep dive 1).

#### Great: Run code in a Serverless Function
One serverless function per runtime; auto-scales with demand; good for CPU-intensive/unpredictable load.
- **Challenge:** cold-start latency; resource limits on long-running/heavy code.

**Decision:** containers — submission volume doesn't vary hugely, and we avoid cold-start latency.

**Pattern — Managing Long Running Tasks:** code execution can take several seconds (containers run code against hundreds of test cases). APIs return job IDs immediately while background workers do the heavy work, preventing timeouts and enabling scale.

Submission flow:
1. API Server receives code + problem ID, routes to the container for that language.
2. The isolated container runs the code sandboxed. The container makes no outbound calls — the managing worker invokes it synchronously (e.g., Docker exec API), waits for completion, reads output from stdout or a mounted volume.
3. API Server stores results in the DB and returns them to the client.

### 4) Live competition leaderboard

Competition definition: 90 minutes, 10 problems, up to 100k users. Score = number of problems solved; ties broken by time to complete (from competition start).

Naive approach: on each `/leaderboard/:competitionId` request, query the submissions table, group by userId, order by distinct problems solved:

```sql
SELECT userId, COUNT(DISTINCT problemId) as numSolvedProblems, MIN(submittedAt) as lastSolveTime
FROM submissions
WHERE competitionId = :competitionId AND passed = true
GROUP BY userId
ORDER BY numSolvedProblems DESC, lastSolveTime ASC
```

In DynamoDB: a GSI with `competitionId` as partition key, then group/sort in memory. Client re-polls every ~5 seconds for freshness.

This puts significant load on the database — optimized in deep dive 2.

## Potential Deep Dives

> **Seniority note:** how proactively a candidate leads deep dives depends on level. In a **mid-level interview it is entirely reasonable for the interviewer to lead most of the deep dives**. Senior/staff+ candidates are expected to proactively anticipate challenges and propose solutions.

### 1) Isolation and security when running user code

Containers already help a lot; harden further with:
1. **Read-only filesystem** — mount code dir read-only; write output to a temp dir deleted shortly after completion.
2. **CPU and memory bounds** — kill the container if limits are exceeded; prevents resource exhaustion.
3. **Explicit timeout** — wrap user code in a timeout (e.g., 5s) that kills the process; prevents infinite loops and helps meet the 5-second result requirement.
4. **Limit network access** — disable network access in the container; in AWS use VPC Security Groups + NACLs to block all but essential traffic.
5. **No system calls (seccomp)** — restrict syscalls the container can make to protect the host.

> In the interview, high-level concepts suffice: "We'd use Docker containers while limiting network access, setting CPU/memory bounds, and enforcing a timeout" is likely enough.

### 2) Making leaderboard fetching efficient

#### Bad: Polling with database queries (current design)
Every client poll triggers a DB query + sort every ~5s. High DB load, poor scaling, potential overload during competitions.

#### Good: Cache with periodic updates
Redis cache of the leaderboard, refreshed from the DB every ~30s; polls hit the cache. Reduces DB load, but updates aren't truly real-time, still polling, and possible race conditions if refresh frequency is too low. Fine for smaller competitions.

#### Great: Redis Sorted Set with periodic polling ← chosen
- On each processed submission, update both the DB and a Redis **sorted set**.
- Key: `competition:leaderboard:{competitionId}`; score = user's total score/solve time; member = userId.
- Update: `ZADD competition:leaderboard:{competitionId} {score} {userId}`.
- Read top N: `ZRANGE competition:leaderboard:{competitionId} 0 N-1 REV WITHSCORES` (ZREVRANGE deprecated since Redis 6.2).
- Endpoint: `GET /competitions/:competitionId/leaderboard?top=100`. Send first pages (e.g., top 1,000); fetch more as the user pages.
- Clients poll every 5s — very fast reads, no expensive DB queries.

**Benefits & tradeoff reasoning:** simpler than WebSockets, near real-time, 5s delay is acceptable, big DB load reduction, scales for this user base. Could use progressive polling (2s in the last minutes of a competition, 10s otherwise).

> Many candidates propose **WebSockets** — not wrong, but **overkill** given modest user counts and acceptable 5s delay. Staff-level candidates articulate the more complex solution but explain why it's overkill here.

### 3) Scaling to competitions with 100,000 users

100k users isn't much — the API server scales horizontally fine. The concern is CPU-intensive code execution in containers.

#### Bad: Vertical scaling
Back-of-envelope: peak of 10k concurrent submissions × ~100 test cases each, at a conservative 100ms/test case ⇒ each submission up to ~10s worst case; 10k submissions = 1M test cases = 100,000 CPU-seconds — you'd need ~1,667 cores to finish in a minute. Largest AWS instances top out at a few hundred vCPUs; also can't scale vertically dynamically, so you pay for an idle giant machine. Not viable.

#### Great: Dynamic horizontal scaling
Horizontally scale the language-specific containers; auto-scaling groups adjust instance counts based on traffic/CPU/memory (AWS: ECS + ECS Auto Scaling). Downside: risk of over-provisioning, but manageable with modern cloud tooling.

#### Great: Horizontal scaling with a queue ← chosen
Add a queue (e.g., **SQS**) between the API server and containers to buffer submissions at peak. Workers pull off the queue; on completion, the worker notifies the App Server, which updates the DB and cache.

**Important consequence:** the system becomes **asynchronous** — results aren't returned immediately. Add `GET /check/:id`, polled every ~1 second by the client; returns results or "processing". (This is literally what LeetCode does — check the network tab on submit.)

> Some candidates introduce WebSockets to avoid polling — could work, but adds complexity that 1-second polling doesn't warrant.

**Tradeoff reasoning:** a strong case exists that the queue is over-engineering at this scale (competitions have registrations, so peaks are predictable and you can pre-scale). The author still chooses the queue because it **enables retries on container failure** and buffers unexpected spikes so no submission is lost. There's no right or wrong answer — weighing pros/cons is the key skill.

### 4) How would the system actually run test cases?

A follow-up designed to break candidates out of "box-drawing mode."

- Don't write test cases per problem **per language** — maintenance nightmare. Write **one set of test cases per problem** runnable against any language.
- Need a **standard serialization** of inputs/outputs plus a **per-language test harness** that deserializes inputs, calls user code, and compares outputs to the deserialized expected output.
- Example — Max Depth of Binary Tree: serialize the tree as a level-order (BFS) array; each language has its own `TreeNode` class that deserializes the array into a tree object, placed alongside the user's code in the container.

```json
{
  "testCases": [
    { "type": "tree", "input": [3,9,20,null,null,15,7], "output": 3 },
    { "type": "tree", "input": [1,null,2], "output": 2 }
  ]
}
```

Define serialization strategy per data structure; ensure each language's harness can deserialize input and compare output.

### Final Design
Client → API Server → (DB for problems/submissions, Redis sorted set for leaderboards, SQS queue → per-language container workers for code execution), with the client polling `/check/:id` for submission results and the leaderboard endpoint every ~5s.

## What is Expected at Each Level?

### Mid-level
- **Breadth over depth (80/20)** — high-level design meeting functional requirements; many components are surface-level abstractions.
- **Probing the basics** — expect questions like "what does an API Gateway do?"; nothing is taken for granted.
- **Mixture of driving and taking the backseat** — drive the early stages; the interviewer may take over later deep dives.
- **The bar for LeetCode (IC4):** clearly defined API endpoints and data model; a functional high-level design meeting requirements; understood the need for security/isolation when running user code and ideally proposed containers, VMs, or serverless.

### Senior
- ~60% breadth / 40% depth; go into detail where you have hands-on experience.
- Clearly articulate pros/cons of architectural choices (scalability, performance, maintainability) and justify tradeoffs.
- Proactive problem-solving: anticipate challenges, identify bottlenecks.
- **The bar (IC5):** speed through the high-level design to spend time on secure/isolated code execution in detail; discuss container vs VM vs serverless pros/cons and justify the choice; get out of box-drawing mode and explain how test cases actually run against user code.

### Staff+
- Not typically asked (question is on the easier side). If asked: drive the entire conversation, proactively identify issues and propose solutions, discuss tradeoffs, cover test-case execution and secure isolation within the 5-second requirement. Ideally design a very simple system free of over-engineering, with a clear path to scale if needed.
